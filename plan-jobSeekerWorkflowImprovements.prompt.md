**Current Resume Generation Methods and Gaps**
- The frontend LLM path builds prompts in `frontend/src/services/prompts/applicationDocsPrompt.js`. It instructs the model to use profile history as source of truth, tailor to the listing, use Australian spelling, and follow ATS-oriented structure. However, it also contains fixed Sam-specific highlights and fallback values for skills, certifications, work rights, and clearance.
- The frontend no-key path uses `generateClientSideTailoredDocs()` in `frontend/src/services/generationService.js`. It emits a fixed resume and cover-letter template with specific employers, metrics, certifications, and work-rights claims even when those facts are absent from the supplied profile. This is a material accuracy risk for a multi-user product.
- The browser's selected provider/model is not preserved through every fallback. The client first attempts its selected model, then can call the backend `/api/jobs/{job_id}/generate` route; that route uses the server-configured model and `DashboardApp.profile`. Server startup loads a shared profile file and may overlay the most recently updated `user_profiles` row, so a fallback can generate from another person's CV/profile instead of the current user's upload.
- Uploaded CV parsing is a separate LLM prompt and quality boundary in `frontend/src/services/parsers/resumeParser.js`. It truncates inputs to 8,000/9,000 characters, uses example values such as Australian citizenship and target salary in the requested JSON schema, and silently falls back to heuristics. The heuristic parser can infer a default title/industry, add skills from industry templates, and assume Australian work rights. Long CVs and CVs from other countries/industries can therefore yield incomplete or invented profile facts before generation even begins.
- The backend `OpenRouterDocumentGenerator` loads source documents, guidelines, and examples through `prompt_context.py`, prompts for verified facts, uses temperature 0.3, and runs a `ContentLibrary.validate_claims()` check. That validator uses regex-extracted facts and is not reliable proof that every generated claim is supported; if source documents are missing, the current path can mark claims verified by default. Its cache key also fingerprints only limited profile fields and the first 500 characters of the job description.
- The deterministic backend fallback in `documents.py` uses a relevance check and ranks achievements by simple skill-string occurrence, but writes largely canned cover-letter prose. The separate `ats_optimizer.py` formatter produces a single-column DOCX from profile fields; when the summary is missing, it inserts generic unsupported-sounding boilerplate, and it does not deeply tailor achievements to the job.
- There are conflicting standards across the master prompt, frontend prompt, backend prompt, fallback, and formatter, including heading names/order, target-title treatment, resume length, referees, and bullet construction. The master prompt explicitly notes an unresolved conflict between two format conventions.
- `runDocumentQualityAudit()` checks structural proxies such as title/keyword presence, table syntax, number count, referees, clichés, and cover-letter length. Its 80-point threshold does not establish factual provenance or relevance, and keyword/metric presence can pass without being correctly evidenced. Some generation paths save or return generated content before this audit; the auto-apply path records a score but does not block dispatch on failed checks.
- The UI labels a score-based pass as “VERIFIED PASS — READY TO SUBMIT”; the score is not evidence verification. The direct provider and backend paths can also save/return drafts before a hard factual gate. This status must not imply claims were checked against the uploaded CV.
- Generation prompts transmit CV/profile text and personal details to the selected external LLM or platform AI proxy. Disclose the provider/model and data handling before upload/generation, minimize fields sent when not needed, and do not place raw CV text or secrets in application logs.
- Existing tests largely verify templates and structural assertions. They do not yet establish that claims trace to candidate evidence, that profile/job changes invalidate cached documents, or that the final PDF/DOCX is complete, legible, and consistent with its source text.

**Current Signup and Profile Isolation Gaps**
- Email/password registration already exists and `authService.registerWithEmail()` initially creates an identity-only profile with blank career fields. However, backend `handle_register()` then calls `migrate_default_user(new_user_id)`, which reassigns all `default_user` applications, profiles, preferences, generated documents, and candidate matches to that new account. A new signup can therefore inherit another person's data.
- The live profile endpoints have fallback behavior that is unsafe for self-service multi-user accounts: a missing profile may resolve to the latest profile, and profile bootstrapping can supply `Technology & IT` and `Melbourne, VIC`. Missing data for a valid new account should be empty, not filled from another account or a developer profile.
- Frontend profile templates include Sam-specific and other sample personas. `profileStorage.js` can select a Sam/first profile in its guest fallback, while other services import `DEFAULT_USER_PROFILE`/`CANDIDATE_PROFILE`. These examples must be isolated to an explicit demo/template chooser and never used as a real account's implicit initial data.
